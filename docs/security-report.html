Breaking into Fayr

We spent a day trying to break into Fayr on purpose. Not by guessing passwords, but the way it really happens: somebody who has the app on their phone, has a perfectly good account of their own, can see every address the app calls, and wants other people's money and other people's details. This page says what we tried, what we found, what we fixed, and what still needs a decision.

Every attack on this page is a test that runs on every change, so if one of these ever starts working again, it fails before anybody ships it. Checked on 27 August 2026 against the working copy, not the copy being shown on Monday.

The attack that empties real companies

It is almost never a broken password. It is this: a person signs in completely normally, then changes one number in the address the app is calling, and reads somebody else's record. Every single screen has to get that right on its own. There is no one place you can check instead.

So we made two real accounts, gave them two real sign-ins, and had the first one try to reach everything belonging to the second. Her offers. Her wallet. Her requests to be paid. Her bank details. Her messages to us. Her chat. The photos she sent as proof. Her name and phone number.

Every one was refused. And they are refused in the safer of the two possible ways: Fayr says "there is nothing here" rather than "that is not yours". Saying "not yours" would confirm to a stranger that the record exists and belongs to somebody.

The worst thing we tried was asking Fayr to send our money to her bank account. It was refused. And to be sure that refusal is real and not an accident, we deliberately broke it, watched the test fail, and put it back. A test nobody has watched fail is not a test.

The three real problems, and what we did

1

Fayr was not telling browsers to protect themselves Fixed

Every answer Fayr sent carried no protective instructions at all. It did helpfully tell the world what it was built with, which is free reconnaissance for somebody deciding how to attack it.

Why this one actually mattered here, rather than being a box to tick: Fayr serves pictures that people themselves sent us. Without an instruction not to guess at what a file is, a browser can be talked into treating one of those uploads as a web page and running it — on Fayr's own address, which is where a staff member's sign-in lives. Two instructions close that off, and they are now on every single answer, including refusals.

One of these instructions is dangerous to get wrong. It tells a browser "only ever use the secure version of this site, for a year". Send it by mistake from a laptop that is not using the secure version and you have locked yourself out of your own machine, and you cannot take it back. So it is switched on only in the real production setting, and there is a test that checks it is absent everywhere else.

2

A phone number was travelling inside a web address Fixed

When a staff member looked somebody up by phone number, the number went into the address. An address is the most copied thing on the internet: it goes into Fayr's own records of what happened, into the records of anything sitting between the laptop and the server, and into the browser history of that laptop, where it stays.

This took two goes, and the first one looked finished. We stopped recording the address's extra part and checked the real records again — the number was still there, because the address itself was being recorded whole. It is now cut off at the question mark, which keeps the useful half (which screen was opened) and throws away the half that can carry a person. Then the search itself was changed so the number is sent privately instead of in the address at all.

Both times we checked by reading what Fayr actually wrote down, not by reading the instructions that were supposed to make it do so. That distinction is the whole reason the first fix was not enough.

3

One invisible character could break the new chat Fixed

There is a character no keyboard produces, which can only get into a message if somebody puts it there on purpose. Sending it in a chat question made Fayr answer with a raw database complaint — which both failed, and told whoever sent it something about how Fayr is built underneath.

It is now refused politely, and not quietly cleaned up. Cleaning it up would have broken a promise we care about: a question is stored exactly as the person typed it, because tomorrow's answer gets written from those words, and a tidied copy hides the spelling and phrasing that are the most useful part.

What we checked, and what we found

Every address
All twenty-four groups of addresses require a sign-in, except the two that cannot (signing in itself, and the "is the server alive" check). Every one is protected at the top level, so a new screen added tomorrow inherits it rather than having to remember. Already right
Guessing addresses
Changing an identifier in an address gets nothing. An identifier that is not really an identifier is refused outright rather than searched for. No staff screen opens with an app sign-in, and — the direction people forget — no app screen opens with a staff sign-in either. The two are separate worlds and neither can verify the other's pass. Already right
Signing in
Asking for a code is limited to five tries a minute, checking one to ten, and staff sign-in to ten. Codes and passwords are stored only as a one-way scramble, never as themselves. Sign-ins expire, and the long-lived pass is swapped for a new one every time it is used, so a stolen one is noticed. We added a limit to two doors that only had the general one. One small fix
What leaks
We read what Fayr actually writes down, not the code that writes it. No phone number, no password, no code, no pass. Message bodies are never recorded at all. Phone numbers in the log are shown with most digits hidden. One fix, above
Hostile input
Fourteen of the classic break-the-database strings, sent at the newest search in the project and again through the app. Nothing was destroyed, nothing was obeyed, and the words were stored exactly as typed. Every hand-written database instruction in the whole project passes a person's words as a separate parcel rather than gluing them into the instruction. Already right
Uploaded photos
Checked by what the file actually is, not what it is called. Size limited. Stored outside anything the public can reach, and only handed back through a door that checks who is asking. A made-up address cannot reach one, and there is a guard against an address that tries to climb out of the folder. Already right
Secrets in the project
We searched all two hundred and twelve saved versions of the project, not just the current one. No keys, no passwords, no certificates — ever. The three near-misses are an obviously fake example used in tests. The one file that does hold real settings has never been saved into the project and cannot be. Already right
Which websites may call us
A named list, never "anybody". With no list set, a real production server allows nothing at all, which is the safe direction to fail in. Already right
The four staff teams
Every team tried against every other team's work. Customer support cannot approve a payment. Finance cannot write an answer users will read, and cannot publish an offer. Only an administrator sees the record of who did what. The teams are separated by the server, not by what the screen chooses to show — which is the difference between a real wall and a curtain. Already right
Money
We tried to take money that was not ours: asking for a payout with an empty wallet, asking for more than we had, asking for negative and fractional and absurd amounts, and sending two requests for the same money at the same moment. All refused, and every movement of money still adds up to exactly zero afterwards. Already right

The three things that need a decision from you

A

The wallet has no floor in the database Your call

Tickets cannot go below zero: the database itself refuses. Money can, if something ever asks it to directly. Nothing can ask it to today — every door that moves money checks the balance first, and there is a test proving that — so this is a second lock missing, not an open door.

It is not fixed yet on purpose, because adding the floor decides something you have not decided. Our own terms say that if somebody deletes their review after being paid, Fayr may take that money back out of their wallet. If the wallet is empty, does that stop at zero and the rest becomes a debt, or does the wallet go negative? Put the floor in first and the answer is decided by accident. Tell us which, and the fix is a few lines.

B

Three warnings need a big upgrade of a core part Your call

The automatic check on the outside parts Fayr uses reported six warnings. One was fixed on the spot with no risk. The other five need more thought:

Three are in the tool that manages the database, and they are only reachable while we are building — that tool is not part of the running service. Clearing them needs moving to the next major version of that tool, which is the single most central thing in the project. Worth doing on a quiet day with a full test run, not today.

Two are in the spreadsheet library used for staff reports. The only offered fix is going backwards to a version from several years ago, which would break the reports. We checked how the library actually uses the affected part: it never uses it in the way the warning is about. So the warning is real and the fix is worse than the problem. Leave it, and revisit if a proper fix appears.

C

The one file that holds real settings Worth knowing

There is a settings file on this laptop holding real identifiers for the text-message service, and an email address. It has never been saved into the project and cannot be — that is deliberate and correct, and we checked every saved version to be sure.

Two things worth knowing anyway. Anything in that file should be treated as needing replacement if the laptop is ever lost or shared, because a file that is safe today is only safe while the machine is. And when we eventually switch on the language model, its key goes in that same file and nowhere else — never in the project, never in a message, never in a conversation with a tool like this one.

What this page does not cover

Said plainly, because a security page that reads as "everything is fine" is the least useful kind.

This was a day of deliberate attacking by the people who wrote the code. That finds the mistakes we are capable of making. It does not replace somebody from outside trying, with no knowledge of how it was built, which is a different and better test and worth paying for before real money is at scale.

Nothing here covers the machines Fayr will eventually run on: who can log into the server, how the database is backed up, who holds the production keys. None of that exists yet, so none of it was checked. It becomes the most important section on this page the day it does.

And nothing here tests a person being tricked. The commonest way money leaves a company is somebody being talked into sending it, and no code change prevents that.

Nothing on this page contains a real key, password or phone number, and nothing was copied out of the settings file to write it.
