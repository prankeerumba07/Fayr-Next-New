One number, two routes

Ten defects were found and closed this sprint. Nine of them are the same shape, and it is a shape worth naming out loud: one fact, reached by two different paths, that agree today and drift tomorrow. Every one of them was caught by us, before a user, a marketplace or an auditor got there.

Every claim on this page is traceable to a commit and a test that fails if the defect returns. Figures verified against the live development database, 25 August 2026.

Why this class is the dangerous one

A crash announces itself. A number that is quietly wrong does not. If the price on the screen and the price in the payment are computed by two separate pieces of code, they will match on the day they are written, pass every test, demo perfectly — and then one of them gets edited, and money starts moving against a figure nobody is looking at.

So the rule we now build to is: a number that matters has exactly one definition, and everything that needs it asks that one place. Most of what follows is that rule being enforced after the fact.

The ten

1

A reviewer could correct a payout figure and be told it saved when it had not

The safeguard that stops a double-click paying twice was built from the value being submitted. So a reviewer who went 1 unit → 3 → back to 1 repeated an earlier key, and the system discarded the third press as a duplicate — while the screen reloaded and said "Saved. Corrected to 1 unit."

What it would have done: on the amount control, ₹499 → ₹599 → ₹499 left ₹599 on file and paid it. Landing back on a figure you tried earlier is an ordinary thing for a person to do.

2

The price shown to the user was not the price the refund was based on

The app displayed the offer's listed price; the refund was calculated from what the buyer was actually charged. Worse, a staff-decided refund appeared under the sentence "Couldn't read the item price — refund can't be computed", beneath a refund that had in fact been computed.

What it would have done: every discounted purchase shows one figure and pays another. The first user to subtract them files a complaint we could not answer.

3

We told users we had confirmed a public review page that does not exist

Once a review was live, every platform got the same line: "Review confirmed live · Publicly visible on the product page." Blinkit, Zepto and Instamart have no public review page at all — they mark a rating on the order inside the buyer's own account and publish nothing a stranger can read.

What it would have done: this was on the demo path. The first director to say "show me that review" would have found nothing to show.

4

A comment in our own code was wrong, and the refund rule had been built on it

The code stated that no marketplace tells us which line of an order an item is, so refunds were keyed to the whole order number. Checking the actual pages rather than the comment showed every platform we support does name the line — Amazon by ASIN, Flipkart by its own product id.

What it would have done: two different offers bought in one basket looked like one purchase claimed twice, so a legitimate second refund was blocked — and the reverse case had no guard at all.

5

Twice, a required value was silently filled with a list position

A function was given a required extra argument so the compiler would catch anyone forgetting it. It did not: writing list.map(fn) hands the callback the item and its position in the list, so the argument was satisfied by 0, then 1, then 2. It compiled and ran.

What it would have done: the first offer in the feed told buyers they had 0 days to purchase, the second 1 day, the third 2. Nothing failed anywhere.

It happened twice — once on the purchase deadline, once on the seat count. The second time it was closed differently: the argument is now a shape a list position cannot masquerade as, so the mistake is a build failure rather than a wrong number on a screen. That is the pattern worth carrying forward — make the error impossible, not merely tested for.

6

Two consecutive screens gave two different deadlines for the same seven days

One screen said "within 7 days of joining — by 1 Sep, 4:00 PM". The next said "for the next 6 days… until 1 Sep, 3:59 PM". Same window, computed seconds apart by two routes, disagreeing by a minute and by a whole day.

What it would have done: the exact deadline does not exist until the server creates the claim, so the earlier screen was forecasting. It now states a length and no clock at all.

7

A line under the login boxes told users something untrue

It said the verification code was printed in the server console. With the real text-message provider running, the code is never logged anywhere — only a masked number and a provider reference.

What it would have done: it sat on screen while the demo script says out loud that there is no shortcut behind the real text message. Removed rather than reworded: the app is not told which provider ran, so it cannot say anything true about it.

8

"Type-check clean" had never once been true

One of our release checks ran from the top of the repository, walked into the server code first, and stopped on the very first file — before reading a single line of the phone app it was supposed to be checking. It had been reported as passing because it exited quietly.

What it would have done: nothing it was supposed to catch was being caught. The check is now scoped to the app, and it verifies which files it actually read — because a mistyped path would empty it and it would pass again on nothing.

9

The duplicate-image fraud check ignored every image we had deleted

Reusing one screenshot across accounts is a fraud signal, and the design was for the fingerprint to outlive the photograph so the signal survives deletion. Writing the test that claimed exactly that showed the check was skipping deleted images — so the signal died the moment the file did.

What it would have done: a 90-day retention policy would have quietly become a 90-day amnesty. Found by asserting the behaviour we had described, not by reading the code.

10

A column documented as the authoritative price is empty on every record

Found this week. A database field described in our own notes as "the real value" is filled from an older, ambiguous source, so it is empty for every purchase the current code creates. Nothing reads it, so nothing on any screen is wrong — the note describing it was the hazard, because it invited someone to build a report on it.

What it would have done: any report written against that column would have shown zero rupees for every task, while the app displayed the correct figure. Caught as a trap rather than as a bug — which is the cheapest possible place to catch it.

The part that is not a success story

Two of these had already paid out real money

The rule that an offer must have caused a purchase did not exist until this sprint. When it was added, every task then in the system failed it — including two that had already been refunded, one for a purchase made seventy-one days before the offer was claimed. They were internal test accounts, so there is nothing to recover, and they are exempted by a single dated line in the code rather than quietly ignored.

Say this if it comes up. It is a far better answer than a clean sheet nobody believes.

What actually changed, beyond ten fixes

  • Every one is now guarded by a test that fails if it returns. A fix without that is a fix with a shelf life.
  • Three were found by writing the test that claimed the opposite. Describing intended behaviour precisely enough to assert it is what exposed the gap — the duplicate-image check, the deadline contradiction and the empty column all surfaced that way.
  • The best fix removes the possibility, not the instance. The list-position defect came back once. The second time it was closed so that the mistake cannot compile.
  • Nothing on a screen states a number the server did not send. Where a figure is missing, the app now says nothing rather than showing a zero — a zero reads as an answer.

If you are asked one question, expect this one

"How do you know there isn't an eleventh?"

We assume there is. Nine of the ten were the same shape, so it is now searched for deliberately rather than stumbled upon, and the tenth was found while looking. The honest answer is that this is a rate of discovery, not a finish line — and a team that can tell you the shape of its own worst defect is further along than one that reports none.
